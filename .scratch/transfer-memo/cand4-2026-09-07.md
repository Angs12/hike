## 2. What the memo caches, and the transfer's dependency structure

The transfer for edge (p → v) = `denote_block_with_stores ~source:p
(get p) ~target:v` (`:2425-2452` @ main): `denote_defs` over p's defs
(pure in the in-state), then `denote_jump` (`:2314-2417`) which per jump
(a) assumes the jump condition — which can **acquire landmarks** (side
effect, `acquire_unsat_fallthrough` `:2015-2055` → `observe_unsat_var`),
and (b) runs the **inline deep walk** `refine_edge_inline` (`:2229-2311`)
for conditional jumps, which consults `Walk_memo` (`:2269`) and on a miss
runs `refine_edge` (`:1477-1564`) — the backward fixpoint whose pops
(`:1513`) record visited blocks into the `~reads` ref (`:1517-1519`) and
spend the C1 budget (`:1515-1516`).

The transfer's **read set** accumulates as: the walk's visited blocks
(per refined jump, unioned at `:2357`) ∪ the block's own tid (`:2449`) ∪
the pred `p` (`:2737`). This set is what `stamp` materializes. **The
walk-hit arm returns `Tid.Set.empty` instead** (`:2271-2272` — "Walk reads
subset the transfer reads") — load-bearing for §4.

`denote_block_with_stores`/`denote_jump` are **internal** (not in
`cbat_vsa.mli`; only callers are the three sites in `cbat_vsa.ml` —
`:2412` inside the module, the miss `:2730` and the re-run `:2719`).

## 3. The read-set/stamp cost shape (the card's load-bearing unknown)

**Answer: NOT ~1. On the heavy real-binary subs it is ~100-512+; on the
small fixtures it is ~1-10.**

- `refine_edge`'s `~f` adds one block tid per pop (`:1517-1519`); pops are
  capped by `~steps` (the C1 dynamic cap, max 256). Measured anchors:
  grep `sub_e350` post-C1 342,548 pops / 1,613 walks ≈ **212 avg**; ls
  `__strftime_internal` 239k/935 ≈ **256, all truncated at the cap**
  (`.scratch/perf-profile/profile-2026-09-05-coreutils.md:95-99`); the
  274a883 commit message records pops 310,272 / blocks 311,123 ≈ 1
  distinct block per pop. So a truncating walk's read-set ≈ the cap.
- The per-block transfer read-set is the **union over the pred's refined
  (conditional) jumps** (`:2357`), so a pred with 2 guarded jumps can stamp
  ~2× the cap. cksum_avx2's autopsy: `WALKS-AT-TRIP pops 1792 blocks 1799`
  over 7 walks ≈ 257/walk (`.scratch/cleanup-8/candidate-3-tripwire.md:32`).
- Consequences per **store**: a `(Tid.t * int) list` of ~212-512+ tuples +
  two `Map.set`s + two record copies (`:2738-2747`) + retention of the old
  entry's value. Per **lookup**: a validity walk of ~212-512+ `ver_of`
  `Tid.Map.find`s (`cbat_memo.ml:51-52`). Per **entry, for the whole
  run**: one retained `AI.t` (a full abstract state) per CFG edge — the
  memo's memory footprint on a 2,950-block sub is thousands of pinned
  states.
- The fixture corpus' walks "terminate naturally well below 256" (pops 3
  orders smaller — `.scratch/c1-walk-budget/spec.md:30-33`), so stamps there
  are tiny — the memo's bookkeeping cost is a **real-binary** phenomenon,
  which is exactly where the hit-rate records disagree.
- Corollary (not in the card): the C1 budget already shrank stamps — a
  budget-limited walk visits fewer blocks, so the stamp shrinks with it.
  The stamp cost scales with the SAME cap the walk budget controls.
- The walk-hit arm's `Tid.Set.empty` (`:2272`) makes stamps tiny ({p, b})
  whenever the inline walk hits Walk_memo — so the stamp-cost and the
  walk-hit-rate interact (see §4 for why that is the audit's problem).

## 4. The version-oracle soundness audit

**Method:** enumerate every mutation of `fs_sol`/`fs_versions`/`rc_state`
in `src/` (grep `fs_sol|fs_versions|rc_state :=|rc_state =` across src/, all
hits read). Writers found:

1. `rc_cell` init (`cbat_vsa.ml:2638-2645` @ main): seeds `fs_sol` from the
   initial solution; `fs_versions` stays empty (`ver_of` = 0). Pre-memo
   (before any find/add) — sound.
2. `set` (`:2651-2663`): the ONLY fs_sol/fs_versions writer; **always
   bumps the written block**.
3. `Walk_memo.add` (`:2287-2296`) and `Transfer_memo.add` (`:2738-2747`):
   write only their own memo field inside a fresh `rc_state` copy — never
   `fs_sol`/`fs_versions`.

Everything else the transfer reads is either **static per run**
(`rc_flag_states`, `rc_call_facts`, `rc_live_in`, `rc_blocks`,
`rc_walk_cfg` — built once in `mk_rctx`, never mutated) or **irrelevant to
values** (`rc_walk_budget` affects walk extent only; a longer-walk result
reused at a shorter-cap moment is sound the same way Walk_memo reuse is —
"a hit is a free, real refinement", `.scratch/c1-walk-budget/spec.md:62`).
`Cbat_landmarks.lm_env` is mutated (`clear_head`, acquisition) but transfer
*results* never read it (acquisition is write-only during transfers;
`lm_calc_steps`/`translate_to` run in process_vertex's widening arm), so it
needs no version.

**Verdict on the oracle itself: EXACT.** Every path that changes a block's
OUT-state (`fs_sol`) bumps that block's version, because `set` is the only
writer and it always bumps. A Transfer_memo entry cannot go stale through
any fs_sol mutation it did not stamp. **This half of the memo is sound.**

**One latent window found — the stamp is INCOMPLETE in the walk-hit case.**
When the inline walk hits Walk_memo during a transfer-miss fill, the
walk-hit arm returns `Tid.Set.empty` (`:2272`), so the transfer entry is
stamped with only `{p, b}` — the walk-read blocks W that produced the
(walk-refined) result are NOT in the stamp. Mechanism, code-verified:
the Walk_memo entry was validated at fill time T1 (W's versions matched
entry creation), the transfer entry validates at lookup time T2 against
{p, b} only; if some `w ∈ W` bumps in T1→T2 while p, b do not, the memo
returns a result whose walk-narrowing reflects `fs_sol|W@T1`. Fixpoint
states only grow monotonically (join/widen upward), so the T1-derived
narrowing can be strictly narrower than T2-correct — an unsound-narrowing
shape (principle #5's array_local class), not merely lost precision. The
code comment's justification ("the walk's own read-set is a SUBSET of the
transfer's (both are keyed on the same versions)", present since
introduction — `git show 7246709:src/cbat_vsa/cbat_vsa.ml:2900-2903`)
conflates the version ORACLE being shared with the read SETS coinciding;
the walk reads upstream blocks directly from the snapshot, unmediated by
p's in-state, so W ⊄ {p, b} in general.

Reachability requires (a) Walk_memo hits inside transfer fills (Walk_memo's
own hit-rate record is contradictory: 0 hits/5,280 lookups on the
2026-09-04 tree — `.scratch/version-stable-key/spec.md:10-11,67` — vs
38.9% recorded on the 2026-09-05 tree — `.scratch/c1-walk-budget/spec.md:27`;
current-main regime unmeasured) and (b) a W-block bump between fill and a
later same-pair lookup. **Frequency unknown; never observed — because
no gate has ever run memo-on vs memo-off; the memo is always on.** This
window is pre-existing (since 7246709), NOT a reason to delete (the card
does not claim it), but it upgrades the A/B's byte-identity gate from
"perf control" to **first-ever stale-hit detector**: memo-on/memo-off IR
byte-identity 35/35 ⇒ the window never fired observably on the gate
corpus; ANY diff is a stop-and-report (either the window fired, or the
deletion is buggy — both are findings, and the distinction is the
diagnosis work, not a silent fix).

## 6. The re-run path's frequency question

**Not instrumented.** No counter wraps the `:2716-2727` re-run; its cost
lands inside the `Denote` stage seconds (the whole per-pred match,
hit arm included, is inside `Stages.time `Denote`` at `:2712`). This also
means stage_timer's `denote` column conflates three different regimes
(miss = full denotation; hit without re-run = find only; hit with re-run =
find + near-full denotation) — one more reason the memo's net effect is
invisible in stage counters and only a wall A/B answers it.

Bounding reasoning from the code (not a measurement): the re-run needs
p inside a WTO cycle (`head_opt = Some`) AND `fired` — acquisition fired
during that specific transfer. Acquisition only fires while
`widening_at_head` is set and an unsat meet occurs (the ascent/warmup
phase of a head); post-stabilization there is nothing to acquire, so
`fired` entries stop re-running. Expect concentration in the ascent
phase; frequency otherwise unknown.

## 7. The precedent (shared-memo) — what transfers, what does not

`.scratch/shared-memo/spec.md`: candidates 5+11 merged — a whole-map
produced-value memo keyed `(block, solution version)`, value = the
complete def→produced-value map for that version; tickets 01-03 merged
(`16e8f4a` + fixture `d3e3eed`), then **REVERTED same-day** (`c0d7ffd`):
producer **+18%** on both reference binaries, zero subs improved,
precision untouched, IR byte-identical (`spec.md:8-16`). Also related,
measured and recorded in `73b4756` (2026-09-04): per-def produced-value
memoization had "nothing to win" (computed on 0.09% of def visits); the
reversed-def-list cache REGRESSED +3-7% ("per-visit overhead beats the
saving whenever the unit of work is small").

**What transfers to Transfer_memo:**
- The discipline: wall time is the only accepted proof; same-day
  build→measure→revert cadence; a memo that cannot measure its own win is
  complexity for nothing (ADR-0006, cited by the shared-memo spec
  `:72,83` and the hotloops card's bar).
- The specific warning in its "worst case is status quo" reasoning
  (`spec.md:83`): for the whole-map shape that reasoning was FALSIFIED —
  the per-visit build/lookup overhead beat the saving everywhere. The same
  claim ("a miss is today's cost plus one lookup") must be wall-proven for
  Transfer_memo, not assumed — which is exactly the A/B.

**What does NOT transfer:**
- The +18% number. Different shape end to end: shared-memo stored a whole
  def→value map per (block, version) — enormous entries, one per block,
  built per visit; Transfer_memo stores one `(AI.t * bool)` + a stamp per
  CFG edge, and its fill is a byproduct of a computation the fixpoint runs
  anyway. The sign of one says nothing about the sign of the other.
- The reach: shared-memo tried to deduplicate denotation ACROSS the vertex
  and walk paths; Transfer_memo deduplicates the same-edge transfer across
  REVISITS — a surface that shrank ~57% when the C8 worklist replaced the
  recursive driver (`9784985`; AGENTS C8 section: e350 visits 2,334→996).

## 11. Verdict — what the evidence supports NOW (pre-A/B), with confidence

- **Mechanics (high/verified):** every card claim about the mechanism
  checks out — the find/stamp/add shapes, the two-Map.set + record-copy
  store, the per-entry version lookup walk, the always-bump `set`, the

  real binaries — it is ~212-512+ tuples per heavy-sub edge, scaling with
  the same walk cap the C1 budget controls.
- **The hit-rate records (high confidence in the resolution):** all three
  are POOLED Walk+Transfer readings through shared module-level counters;
  none isolates Transfer_memo. The apparent contradiction is sample
  composition (different subs, one pathological mid-ascent case), not
  instability — the trees in question are IR-byte-identical, so per-sub
  rates are tree-stable. The only near-pure Transfer sample (cksum_avx2
  at trip: 0.09% hits, 74% stale) is the memo's worst regime. A clean
  Transfer-specific rate on a normal heavy sub has never been measured.
- **The net wall effect (the gap, confirmed):** never measured since the
  C8 worklist replaced the recursive driver the memo was built for. At
  introduction it measured hot-sub −22% / whole-binary neutral under the
  OLD driver — i.e. the memo was earning once, and its earning surface
  (repeat consultations) has since shrunk ~57% on the worst sub. Prior
  expectation: deletion likely neutral-to-slightly-positive on wall
  (near-pure-sample 0.09% hits + 1.1-7.1% on six heavy subs + the
  stamp/retention costs nobody has priced), but ls sub_4bbd's pooled 49.7%
  — attribution unknown — could carry whole binaries; whether any of this
  clears ±2% on producer totals is genuinely open. The A/B is the only
  honest answerer.
- **Soundness audit (high confidence in the mechanism, unknown in
  frequency):** the fs_sol version oracle is EXACT (single writer, always
  bumps); the memo's one latent hole is the walk-hit arm's dropped walk
  reads (since introduction) — a stale-hit window that leans unsound

  testable before — the memo was never off), and NOT a deletion argument
